## 1. Executive Summary

项目完成度与工程纪律高于平均水平：配置驱动、三层漏斗、反馈学习闭环的设计取向全部正确。
当前 2 用户运行良好，但**迈向 50 用户目标前有三个必须解决的结构性问题**:

| # | 问题 | 影响 | 修复方向 |
|---|---|---|---|
| 1 | 反馈通道不校验发件人，任何人可伪造标注污染他人学习词表 | 中危安全漏洞，全自动学习会放大投毒 | From 校验(数行代码) |

## 2. 系统现状快照

```
每日流水线(main.py,cron 触发,per-user 串行):
  python -m feedback            # IMAP 收集回信 → 词表学习闭环
  python main.py                # 对每个 active 用户:
    PubMed(严格/宽松降级) + bioRxiv(全量本地过滤) → 合并去重
    → 规则粗筛(关键词加权 + 期刊分层 + learned 词加分)
    → 跨天去重 → journal_fallback 低相关兜底 → top-15
    → AI 处理(分析/新闻/翻译,逐篇逐用户调用 LLM)
    → 六维加权精排 + AI 推荐理由 → 配额定级(3/5/7)
    → 入库 SQLite → 每日价值总结 → HTML 邮件(含反馈链接)
每周流水线(weekly_report.py): 聚合 SQLite 近 7 天推荐 → 统计 + LLM 趋势总结 → 周报
```

关键资产(应保留):配置驱动治理、三层漏斗成本控制、Rocchio 式词表学习(提权护栏/降权克制/半衰期/审计日志)、per-user 故障隔离、幂等写入、密钥卫生。

## 3. 审查发现汇总

### 3.1 架构与工程(7 维度结论)

| 维度 | 结论 | 关键证据 |
|---|---|---|
| 系统架构 | 分层合理，但"每用户一条完整流水线"的分工导致重复计算与粗粒度失败 | `main.py:125-155`:LLM 产物逐用户重算，持久化在 rank 之后，单篇失败丢全天 |
| 筛选策略 | 内容过滤方向正确，精度机制有缺口 | 子串匹配无词边界 `scorer.py:96`;无语义层;无多样性重排 |
| 数据库 | 容量够 50 用户，一致性/并发/迁移有缺口 | 无 users 表(email 字符串为身份键);无 WAL/busy_timeout;无 schema 版本;`paper_analysis` 缺 `field` 列 |
| Prompt 维护 | 文件化好，变更治理为零 | JSON 剥离逻辑重复 4 处;`.env.example` 的 `OPENAI_MODEL` 是死配置(`llm.py:29` 只读 model.yaml) |
| 多用户扩展 | 架构可，成本/时长不可 | 每用户 ~60–75 次 LLM 调用串行;`LLMClient` 无超时/429 退避/max_tokens/预算 |
| 安全 | 一个中危，两个低危 | 反馈伪造(`collector.py:29` 不校验 From);摘要 prompt injection + learned term 查询注入;用户 PII 入 git 历史;依赖未钉版本 |
| 可维护性 | 纪律好，有死结构与重复 | `scheduler/` 空目录 + `schedule` 死依赖;`biorxiv._term_groups` 与 `pubmed.build_queries` 手工同步;测试全 mock 无集成测试;`docs/ARCHITECTURE.md` 缺失;`main()` 恒返回 0 致失败静默 |

### 3.2 推荐管线六项判断

| # | 问题 | 判断 | 依据 |
|---|---|---|---|
| 1 | 召回不足 | **是** | 检索词天花板 + `retmax=50` 硬顶;`journal_fallback` 只在已召回池内递补(`scorer.py:141`)不扩召回;cron 漏跑无回补;数据源仅 2 个 |

## 4. 优化方案(V4 推荐系统摘要)

核心思想:**不动骨架,动分工** —— 把管线拆成"全局摄取层(每天一次,用户无关)+ 个性化层(每用户轻量)"。

```
全局摄取层(每天 1 次):
  PubMed(实验室级宽查询 + 各用户查询合并去重) + bioRxiv + RSS
  → 统一候选池全局去重
  → 论文级 LLM 产物每篇只做一次入库:分析 / 新闻 / 翻译 / ★embedding

个性化层(每用户):
  多路召回:① 关键词通道(现有词表+learned terms,加词边界)
           ② ★语义通道(用户画像向量 vs 论文向量 cosine)
           ③ 期刊守望通道(当日 T0/T1 全量,替代事后递补)
  → RRF 融合 → 跨天去重 → 候选 ~30 篇
  精排:★Listwise LLM 一次调用相对打分(替代 30 次绝对分)
       特征融合(向量相似度/关键词/期刊/时效/新颖性),
       ★每用户在线修正权重(反馈驱动,向全局权重贝叶斯收缩)
  → ★MMR 多样性重排 → 配额定级(保留 0 分护栏) → 特征落库
```

反馈学习从"一维词表"进化为"三维":**词表(保留)+ 向量质心画像(正/负反馈质心,同款半衰期衰减)+ 排序权重在线学习(乘法权重更新)**。全部沿用现有护栏哲学:≥2 次支持生效、负信号只降权不硬排除、JSONL 审计可回滚。

数据模型增量:`users` 表(yaml 同步)、`paper_embedding`、`user_profile_vectors`、`recommendation_features`(全量特征落库 → 排序可离线回放实验)、WAL + busy_timeout + schema_version。

**量化预期**:每用户 LLM 调用从 ~75 次降至 ~5 次;50 用户总时长从 100 分钟级降至 15 分钟级;新用户冷启动从"手写 251 行词表"变为"静态画像向量即日可用"。

## 7. 明确不做(反过度工程)

- 不上深度学习排序模型:50 用户 × 每日个位数反馈撑不起,且违背"透明可回滚"哲学
- 不引入向量数据库/独立检索服务:日候选池约两千篇,numpy 暴力 cosine 毫秒级;SQLite 单文件是既定部署约束
- 不做完整协同过滤:用"实验室级正反馈聚合质心"作为新用户冷启动先验即可,隐私无害且足够

## 8. 风险与注意事项

- **embedding 模型选型**(P1-7)需小样本评估后再全量:通用模型对拉丁学名/方法缩写的效果差异大,建议用既有 save/relevant 历史做选型测试
- **权重在线学习**(P2-9)必须先落特征再开学习,且保留"回滚到全局权重"开关;前两周只观察不生效(shadow mode)
- **重构窗口**(P0-2)期间保持日报不中断:先加缓存读路径,再拆流水线,两步分开上线
- 用户 PII(真实姓名邮箱)已在 git 历史,仓库若变更托管需先评估
